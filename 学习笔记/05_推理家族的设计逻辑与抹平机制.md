## 一、破案：为什么界面上会出现“家庭”？

在后台管理界面的表格和筛选框里看到的“推理家庭”，是**浏览器自带网页翻译软件造成的“翻车现场”**：
- **英文原词**：`Reasoning Family`
- **中文规范技术翻译**：**“推理家族”** 或 **“思考机制系列”**
- 就像我们在计算机科学里常说的 CPU 架构（如 `x86 Family 6`）、大模型族系（`Llama Family`、`Qwen Family`），浏览器按字面死板地翻译成了生活中的“家庭”。

---

## 二、为什么系统需要设计“推理家族（Reasoning Family）”？

### 1. 行业残酷现实：各大 AI 厂商的“深度思考参数”完全在打架！
现在的各大模型厂商都在推出带**思维链（Chain-of-Thought）深度思考**的大模型，但是**每家调用接口传的参数千奇百怪、完全不互通**：

| 厂商 / 模型家族 | 代表模型 | 它是怎么开启思考的？传什么参数？ |
| :--- | :--- | :--- |
| **OpenAI 家族** | o1, o3, o4-mini | 参数叫 `reasoning_effort: "low" \| "medium" \| "high"` |
| **Qwen 家族** | Qwen3, Qwen-2.5-Max | 在 `chat_template_kwargs` 里传 `enable_thinking: true / false` |
| **Anthropic 家族** | Claude 3.7 Sonnet | 参数叫 `thinking: { type: "enabled", budget_tokens: 2048 }` |
| **Always-on 家族** | 部分纯深度推理特化模型 | 思考永远强制开启（`modes: ["enabled"]`），传 `false` 会直接报错拒绝 |
| **传统通识模型** | 普通 Llama 3 8B, 传统 7B | **根本不支持思考功能**，没有思考参数 |

### 2. vLLM Semantic Router 的神级解耦：统一抹平差异
如果没有“推理家族”，管理员在配置路由规则时就会痛苦不堪：
> “如果规则切到 Qwen，我得写套代码传 enable_thinking；如果切到 o1，我又得改代码传 reasoning_effort……”

为了解决这个大难题，vLLM 设计了 **Reasoning Family（推理家族）**：
1. **抽象统一接口**：在路由规则里，管理员只需要统一选择通用的开关：`开启思考`，`挡位: 高 / 中 / 低`；
2. **底层自动转译**：路由器底层根据模型关联的“推理家族”字典（`zz_generated_catalog.go`），**全自动把通用的思考指令，翻译成对应厂商看的懂的具体 JSON 参数发过去**！

## 三、为什么表格里有的写 `Qwen3`，有的写 `不适用`？

看截图里的表格：
1. **第一行 `qwen3-8b`**：它的推理家族标着 **`Qwen3`**。
   - 说明这个模型支持通义千问官方的思考协议，路由器知道如果命中深度规则，该往它的 template 里注入 `enable_thinking: true`；
2. **第二行 `远程-开放-参考` / 普通模型**：它的推理家族标着 **`不适用 (N/A)`**。
   - 说明这是一个普通无思考链的模型（或者单纯做文字补全的模型），没有开启或关闭思考的硬件能力，所以不属于任何推理家族。

## 四、对我们小毛驴架构的落地启示

1. **统一模型网关必须抹平参数差异**：
   - 我们未来既有自建的 DeepSeek/Qwen 本地小模型，又会外接云端的大模型；
   - 在前端管理台统一定义“思考挡位（低/中/高）”，底层按模型家族自动映射具体参数，这是工业级网关最干净优雅的做法；
2. **后台汉化规范**：
   - 界面所有地方必须严谨采用**“推理家族”**或**“思考协议”**，严禁使用“家庭”等机翻字眼，保持顶级专业性。
