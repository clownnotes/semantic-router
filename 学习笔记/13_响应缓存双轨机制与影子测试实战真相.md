## 一、破案：“同样问题秒回”到底是记死答案，还是向量语义？

师弟敏锐地提出核心质疑：
> *“如果字面上多一个字少一个字、语气有变化就不算同样问题，那这个设计就很鸡肋；但如果是用向量判断差不多就秒回，那确实很牛逼。”*

### 源码技术真相：它支持【双轨模式】！

在 `plugin_config.go` 和 `config.yaml` 中，`response_cache` 支持两种截然不同的模式：

| 模式 | 运作原理 | 优缺点与应用场景 |
| :--- | :--- | :--- |
| **1. 精确匹配 (`mode: exact`)** | 对用户的整段提问做哈希计算（MD5/SHA256）。必须连标点符号都一模一样才命中。 | **优点**：极快（0.1ms）、零算力开销；<br>**缺点**：如师弟所言比较“死板”，差一个标点就无法命中。适合固定脚本查询。 |
| **2. 语义向量匹配 (`mode: semantic`)**<br>★ **【师弟说的牛逼机制】** | 把用户问题转化为向量 Embedding，存入向量缓存库（Redis / Valkey / 内存）。新问题进来算**向量相似度**。配置参数：`similarity_threshold: 0.82`。 | **优点**：极聪明！“怎么请假”和“请问如何申请休假”，字面完全不同，但相似度 > 0.82，直接命中，**秒回历史优质答案，大模型调用费用为 0**！<br>**缺点**：需要极微小的轻量 Embedding 提取耗时。 |

### 会不会记很多答案撑爆数据库？
- **不会！** 每一条缓存都挂载了 **`ttl_seconds`（存活时间）**，比如配置 `7200`（2 小时），超时自动挥发淘汰，只保留当下高频热点问题，绝不无限堆积。

## 二、影子分流 (`shadow_dispatch`)：在路由层“暗中练兵”

源码中的配置：
```yaml
- type: shadow_dispatch
  configuration:
    enabled: true
    model: qwen3-32b # 新模型
    sample_rate: 0.05 # 抽取 5% 真实线上流量
    timeout_seconds: 30
```

### 它的价值：
1. **完全不影响真实用户**：主模型（8B）的回答正常吐给用户，影子请求是后台异步复制跑的，用户 0 等待；
2. **零风险考核新模型**：当你想把业务换成一个新模型时，先用影子分流偷偷跑几天，把新模型的回答和耗时记录在日志里对齐验收，万无一失才正式转正！
